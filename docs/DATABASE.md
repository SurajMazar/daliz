# Databases

## Platform database (`daliz_platform`)

| Table | Purpose |
| --- | --- |
| `accounts` | identities: email, Argon2id hash, status, MFA (encrypted secret, last used step), lockout counters |
| `recovery_codes` | MFA recovery codes (keyed hashes, single use) |
| `email_tokens` | password-reset and email-verification tokens (hashed, single use, expiring) |
| `sessions` | session token hash, stage, selected tenant, support session, step-up expiry, device info, expiry/revocation |
| `security_events` | login failures, lockouts, MFA/password changes, new-IP sign-ins, support sessions (retained 365 days) |
| `platform_permissions`, `platform_roles`, `platform_role_permissions`, `platform_admins` | platform RBAC (catalog synced from code on start) |
| `organizations` | customer organizations |
| `tenants` | tenant metadata, status and reason, plan, limits, locale/timezone/currency, activity |
| `tenant_databases` | database name/host/port/role, encrypted password, status, schema version, last migration error |
| `tenant_domains` | custom domains with verification token and verified timestamp |
| `tenant_memberships` | which accounts may enter which tenant (and whether they're tenant admins) |
| `tenant_provisioning_jobs` | provision/migrate/decommission jobs with per-step state |
| `invitations` | invitation token hashes (single use, 7-day expiry) |
| `support_sessions` | audited impersonation sessions |
| `api_keys` | hashed API keys with scopes, expiry and revocation (issuance API ships with the integrations slice) |
| `feature_flags`, `tenant_feature_flags` | global flags and per-tenant overrides |
| `platform_settings` | maintenance mode, platform MFA policy, defaults |
| `platform_audit_logs` | append-only (trigger-enforced) |

## Tenant database (`daliz_tenant_<slug>`)

| Table | Purpose |
| --- | --- |
| `users` | tenant users linked to `accounts.id`; status; optimistic-lock `version` |
| `permissions` | catalog (synced from code on every migration) |
| `roles`, `role_permissions`, `user_roles` | tenant RBAC; built-in roles have `key`, Owner is `immutable` |
| `settings` | `general`, `security`, `branding` JSON values, schema-validated, versioned |
| `branding_assets` | uploaded logos (status, dimensions, palette, storage prefix) |
| `tenant_audit_logs` | append-only (trigger-enforced); includes support-session activity |
| `idempotency_keys` | stored responses for idempotent endpoints (purged after expiry) |
| `ledger_accounts` | chart of accounts (type, subtype, parent, system flag) |
| `journal_entries`, `journal_lines` | double-entry journals; status draft → pending → approved → posted → reversed; `numeric(20,4)` money |
| `number_sequences` | gapless document numbers (row-locked counters) |
| `daybook_entries` | quick income/expense/transfer records, each backed by a journal entry |
| `folders`, `files`, `file_versions`, `file_shares` | library with soft delete (trash), versions (scan status per version), user/role shares |
| `workspaces`, `workspace_members`, `projects`, `tasks`, `labels`, `task_labels`, `task_comments`, `task_attachments`, `task_activity` | planner |
| `calendar_events`, `event_attendees`, `event_exceptions`, `reminders` | calendar (one row per series + exceptions) and reminders |
| `notifications`, `notification_preferences`, `notification_deliveries`, `push_subscriptions` | notification centre and tracked email/push deliveries |

Accounting integrity triggers (migration `0003`): a journal entry can only become posted with ≥2 lines and equal, positive debits/credits; posted/reversed entries and their lines can't be updated or deleted (the only allowed change is posted → reversed); entries can't be inserted already posted.

## Conventions

- UUID primary keys (`gen_random_uuid()`), `timestamptz` everywhere, UTC database timezone. Tenant-local time zones come from tenant settings, never the server.
- Status columns are enums validated in code; state transitions happen via conditional `UPDATE … WHERE status = …` so concurrent requests can't both succeed.
- Mutable admin records carry `version` for optimistic locking (`VERSION_CONFLICT`).
- Multi-row changes (roles with permissions, users with roles, provisioning state, branding activation) run in transactions.
- Audit tables reject `UPDATE`, `DELETE` and `TRUNCATE` via triggers.

## Migrations

Schemas are defined with Drizzle (`src/database/{platform,tenant}/schema.ts`), and SQL migrations are generated by drizzle-kit into `migrations/`. Custom SQL (triggers) uses `drizzle-kit generate --custom`. See TENANCY.md for how tenant migrations fan out, and for the expand/contract rollback strategy.
